# campus-classroom

校园空教室查询工具的产品设计案：需求调研 → 竞品分析 → PRD → 可点击原型。

起因很具体：我自己每天晚上找自习室，都是打开教务系统一格格看课表，走到教室发现有人上课，再换一间。查了 126 份问卷之后发现，**62% 的同学都在做同一件事**——信息是有的，只是没有被加工成"这间教室现在空不空"。

这个仓库记录我怎么把这个问题拆开、验证、最后落成一个可以点的原型。

> 说明：这是**课程/个人项目**，没有真实研发排期，也没有线上数据。所有数字都来自我做的问卷与访谈（原始方法见 [docs/research.md](docs/research.md)），原型里的教室数据是模拟的。

## 直接看原型

打开 [`prototype/index.html`](prototype/index.html) 即可（单文件，无依赖、无构建）。

可交互的点：

- 切换时段（现在 / 今晚 / 明早）→ 列表与"可用至"同步变化
- 筛选（有插座 / 20 人以上 / 只看 A 楼）→ 无结果时有空状态与"清除筛选"
- 点教室卡片 → 底部弹层看容量、插座、今日后续占用
- 某些时段会触发"教学楼都满了"的兜底文案，而不是一片空白

## 调研结论（摘要）

| 结论 | 数据 |
| --- | --- |
| 需求是高频刚需 | 75% 每周至少查一次 |
| 现有方式靠人肉推导 | 62% 自己看课表推，39% 直接去碰运气 |
| 主要痛点是"不准"不是"没有" | 访谈 12 人中 7 人提到调课滞后 |
| 交互必须极短 | 91% 要求 3 步内拿到答案 |
| 插座是硬需求 | 排序第三，仅次于准确性和距离 |

两个被数据推翻的假设（写在 research.md 里）：以为大家查的是"现在"，实际 68% 查未来时段；以为插座是次要因素，实际排第三。

## 产品决策

从调研到设计，四条结论直接改掉了原方案：

| 调研发现 | 对应决策 |
| --- | --- |
| 数据存在但未被加工 | 核心功能是"把课表算成空教室"，不新建数据源 |
| "查到不准"比"查不到"更糟 | 显式展示更新时间 + 存疑标记，宁可少给不给错 |
| 68% 查未来时段 | 时间胶囊放首屏，一次点击切换 |
| 91% 要求 3 步内 | 砍登录、砍引导页、砍首页推荐 |

明确不做的：图书馆座位预约、社交组队、教室借用申请、多校覆盖。

## 关键设计取舍

**为什么不做众包上报空教室？**
12 人访谈里只有 2 人愿意主动上报。没有激励的众包会退化成"少数人维护、多数人受益"，数据反而更烂。所以纠错只做"存疑标记"（24 小时内 ≥ 3 条同类反馈才标记），不试图替代课表数据。

**为什么把"可用至几点"当核心字段？**
访谈里多人提到"坐十分钟被赶出来"。只知道"现在空"不够，用户真正要的是"能待多久"。这一条是相对教务系统的直接改进点。

**为什么排序是"距离 → 空置时长 → 插座"？**
问卷排序题里这三项是前三。距离优先是因为场景发生在"路上"（research.md 发现 2），用户已经出门了，先要近的。

**如果学校官方做了这个功能怎么办？**
写在 competitive-analysis.md 第 4 节：大概率会做，但落地慢。应对不是拼速度，而是把官方不愿意做的细节做深（插座标注、可用至、多天叠加）。如果官方做好了，这个项目就该结束——作为课程项目，它已经完成了"验证需求"的价值。

## 走查记录

原型做了 5 人走查，发现并修了 3 个问题（时间胶囊不明显、弹层没有关闭按钮、插座图标被当成装饰）。完整记录在 PRD 附录 A，包括**没有修**的那一条及原因。
