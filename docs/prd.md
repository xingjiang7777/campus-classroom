## 1. 背景与目标

### 1.1 问题

本校学生查空教室有两条路径，都不好用：

- **教务系统**：只能看"某门课在哪个教室"，要看"某个教室某时段有没有课"需要反推；且临时调课更新滞后；
- **群里问**：得到的是片段信息，无法规模化。

调研数据（126 份问卷）显示：62% 的学生靠自己推课表，39% 直接去教学楼碰运气；发现"查到了不准"是比"查不到"更严重的抱怨（见 research.md 第 4 节）。

### 1.2 目标

**一句话**：让本校学生在 3 步内、10 秒内，知道"现在/今晚，离我最近的空教室在哪"。

分层目标：

| 层级 | 目标 | 衡量指标（上线后） |
| --- | --- | --- |
| 业务目标 | 降低"走到教室发现有人上课"的无效移动 | 目标用户自报"白跑"次数从每周 1.8 次降到 0.8 次（基线来自问卷 Q5） |
| 产品目标 | 查询任务完成率 | 首屏到"看到可用教室列表"的转化 ≥ 85% |
| 体验目标 | 快 | 首屏可交互 < 1.5 s（4G）；完成一次查询 ≤ 3 次点击 |

**北极星指标**：周活跃查询用户数（WAU），而不是 PV。理由：PV 可以被"反复刷新看有没有空位"刷高，WAU 更接近"真的有人需要这个答案"。

### 1.3 不做什么

明确边界，避免范围蔓延：

- 不做图书馆座位预约（另一个问题，且涉及硬件闸机）；
- 不做社交 / 组队自习（访谈显示学生用微信群就够了，见 research.md 发现 3）；
- 不做教室借用申请（走学校既有流程，工具只做"查"不做"占"）；
- 不做多校覆盖（数据源差异大，先把一所学校做准）。

## 2. 用户与场景

### 2.1 用户角色

| 角色 | 描述 | 核心诉求 | 占比（问卷） |
| --- | --- | --- | --- |
| 自习型学生（主） | 每周自习 3 次以上，常结伴 | 快、准、有插座 | 41% |
| 临时型学生 | 考试周 / 补作业时才找 | 别让我注册，别让我学 | 34% |
| 蹭课/活动型 | 找空教室开会、办社团活动 | 要大教室、能待到几点 | 18% |
| 偶然型 | 极少使用 | — | 7% |

### 2.2 核心场景（按频次排序）

**S1 晚饭后找今晚的自习室（最高频）**
- 时间：18:30–19:30，地点：食堂到教学楼的路上
- 任务：今晚 7 点到 10 点，哪间教室空、有插座、走过去 5 分钟内
- 现状痛点：教务系统要一格格看课表；走到发现被选修课占了

**S2 早八前找空教室自习**
- 时间：7:30–8:00
- 任务：现在这个时段哪间空，能不能待两小时
- 特殊约束：早上很多教室有课，需要"能待到几点"的信息

**S3 社团临时开会找大教室**
- 时间：不固定，多在晚上
- 任务：能坐 20 人以上、有投影的空教室
- 现状痛点：现有工具都不支持按容量/设备筛选

**S4 考试周找长期固定自习位**
- 时间：期末前两周
- 任务：连续几天同一时段都空的教室
- 特殊约束：需要"多天叠加"视图，这是本产品相对竞品的差异点（见竞品分析）

### 2.3 用户旅程（S1）

```
食堂出来 → 打开（或从微信收藏进入）→ 首屏直接是"现在可用的教室列表"
        → 按距离排序，第一条就是最近的教学楼 → 点开看详情（插座/容量/能待到几点）
        → 决定去 → 截图/分享给同伴（可选）
```

关键设计约束：**没有登录、没有引导页、没有首页推荐**。91% 的用户要求 3 步内完成（research.md Q4），任何前置步骤都在消耗这个预算。

## 4. 功能详述

### F1 实时空教室列表

**规则**
- 数据源：教务系统课表（按教室维度聚合），每 10 分钟同步一次；
- 判定"空"：该教室在当前时段内**没有任何课程**，且当前时间不在两节课的课间 10 分钟内（课间视为"即将占用"，标灰）；
- 排序：默认"距离近 → 空置时间长 → 有插座"三级排序；
- 展示字段：楼栋-房间号、当前状态（空闲 / 即将上课 / 使用中）、可空至几点、插座图标、容量。

**异常处理**
| 情况 | 表现 |
| --- | --- |
| 数据同步失败超过 30 分钟 | 顶部黄条提示"数据可能不是最新（更新于 HH:MM）"，列表仍展示但置灰可信度标识 |
| 某教室无数据 | 不展示，而不是显示"空闲"——**宁可少给，不给错信息** |
| 全部教室都有课 | 空状态文案："这个时段教学楼都满了，试试看今晚 9 点后"，并给出一键切换 |

**验收标准**
- 给定固定课表数据，脚本断言 20 个教室的空闲判定结果与人工核对一致；
- 首屏渲染 ≤ 1.5 s（4G，中端安卓机）。

### F2 时段切换

**交互**：首屏顶部一行时间胶囊，默认选中"现在"，另三个是"今晚"（19:00–22:00）、"明早"（8:00–12:00）、"自定义"。

**规则**
- 一次点击完成切换，不弹日历（自定义除外）；
- 切换后列表**原地刷新**，不跳页、不回到顶部（保持用户位置感）；
- 记住用户上次选择，但只在同一天内有效——第二天回到"现在"，避免"看着明早的数据以为现在有空"这种误判。

**验收标准**：从默认状态切到"今晚"，点击数 = 1，列表更新时间 < 300 ms（本地数据）。

### F3 教室详情

底部弹层，不做新页面。字段：

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| 教室号 / 楼栋 / 楼层 | 基础数据 | — |
| 容量 | 基础数据 | 用于 S3 场景筛选 |
| 插座 | 人工标注（首次） | 标注"每人一位 / 靠墙 / 无" |
| 空调 | 基础数据 | — |
| 可用至 | 课表推算 | 显示"可用至 21:40"，而不是"空闲"两字 |
| 今日后续占用 | 课表推算 | 折叠展示，默认收起 |

**为什么强调"可用至"**：访谈中多人提到"进去坐了十分钟被赶出来"，本质是只知道"现在空"，不知道"能待多久"。这一条是相对教务系统的直接改进点。

### F4 数据新鲜度与纠错

- 列表顶部常驻"更新于 HH:MM"；
- 每条教室右侧有"信息有误？"入口（长按触发，避免误点），可选"实际有课 / 实际空闲 / 其他"；
- 纠错提交后不立即改数据（防止恶意刷），进入待核队列，同一教室 24 小时内 ≥ 3 条同类反馈才自动标记"存疑"。

**设计取舍**：为什么不做"用户实时上报空教室"（类似众包）？因为调研显示学生不愿意为工具做贡献（12 人访谈中仅 2 人表示愿意），众包在没有激励的情况下会变成"少数人维护、多数人受益"，最终数据更烂。所以纠错只做"存疑标记"，不试图替代课表数据。

### F5 筛选（V1.1）

筛选条件不超过 3 个，平铺在一行：`有插座` `容量 20+` `只看本楼`。多选即生效，无需"确定"按钮。

不做"筛选面板"：S1 场景用户在走路，展开面板 = 多两次点击。

### F6 多天叠加视图（V1.1）

考试周场景专用：选择"连续 3 天 / 5 天"，只显示**所有天都空**的教室，用一张表呈现"教室 × 时段"的占用矩阵。

这是相对现有竞品的差异点（见 competitive-analysis.md），但 Effort 高、Reach 小，所以放 V1.1。

## 5. 关键流程

### 5.1 主流程（S1）

```
打开 → [本地缓存命中?] --是--> 渲染列表（<200ms）
                        --否--> 请求接口 → 渲染 → 写缓存（TTL 5 min）
     → 用户点某教室 → 底部弹层详情 → 关闭 / 分享
```

### 5.2 冷启动流程

```
首次打开 → 请求定位（可拒绝）→ 拒绝则按"上次访问楼栋/默认楼栋"排序
        → 首次使用有 1 屏说明（仅一次，可跳过）→ 进入列表
```

定位权限被拒绝是常态（约 30%），必须有降级路径，不能卡住。

## 6. 数据与指标

### 6.1 指标体系

| 类型 | 指标 | 定义 | 目标 |
| --- | --- | --- | --- |
| 北极星 | WAU | 周内至少完成 1 次"查看详情"的去重用户 | 上线首月 ≥ 300 |
| 转化 | 首屏→详情率 | 点击任一教室详情 / 首屏曝光 | ≥ 45% |
| 效率 | 查询完成时长 | 打开到点击详情的中位数 | ≤ 10 s |
| 质量 | 纠错率 | 提交纠错次数 / 详情浏览量 | ≤ 2%（高了说明数据不准） |
| 留存 | 次周留存 | 本周使用、下周仍使用的比例 | ≥ 40% |

### 6.2 埋点方案

| 事件 | 触发时机 | 关键属性 |
| --- | --- | --- |
| `page_view` | 首屏渲染完成 | 是否命中缓存、定位是否授权 |
| `time_switch` | 切换时间胶囊 | from、to |
| `room_detail` | 打开详情弹层 | 教室 ID、列表排名、可空时长 |
| `filter_apply` | 勾选筛选项 | 条件组合 |
| `correction_submit` | 提交纠错 | 类型、教室 ID |
| `share_click` | 点分享 | 渠道 |

埋点原则：**只埋能改变决策的事件**。不做"页面停留时长"这类只能看不能动的指标。

## 7. 非功能需求

| 项 | 要求 | 理由 |
| --- | --- | --- |
| 首屏性能 | 4G 下可交互 < 1.5 s | 用户在走路，等 3 秒就放弃了 |
| 离线可用 | 最近一次数据本地缓存 5 分钟 | 教学楼信号差是常态 |
| 兼容性 | 微信内置浏览器 + 主流手机浏览器 | 传播主要靠群分享 |
| 无障碍 | 状态不能只靠颜色区分 | 色弱用户占男性约 8% |
| 隐私 | 定位仅用于排序，不上传精确坐标 | 学生对此敏感，访谈中有明确提及 |

## 9. 风险与依赖

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 教务系统无公开接口 | 数据拿不到，产品不成立 | 先做"课表导入 + 本地推算"的半自动方案；这也是原型阶段只做前端的原因 |
| 课表数据滞后于临时调课 | 准确性下降，用户流失 | F4 的"存疑标记" + 显式展示更新时间 |
| 学校禁止爬取 | 合规风险 | 不爬取，只做用户主动导入 |
| 依赖单一学校 | 无法规模化 | 明确接受：先做准一所学校 |

## 10. 开放问题

1. 课表数据的合法获取方式尚未确认，需要和教务沟通——这是**项目能否落地的前置条件**，不是技术问题；
2. 是否需要"教室实时人数"？目前没有低成本获取手段，摄像头方案涉及隐私，暂不做；
3. 考试周的多天叠加视图，用户是否真的会连续多天去同一间教室？样本只有 12 人访谈，证据不足，需要在 V1.1 前补验证。
